# Raft Interview Prep Notes

This document is your read-aloud reference for the Raft AI Engineer coding challenge. It summarizes what was built, why it was built that way, and sample answers for likely questions.

## Project summary

I built a small AI agent that:

- Accepts a natural language request such as "Show me all orders where the buyer was located in Ohio and total value was over 500."
- Calls a dummy customer API that returns messy, unstructured text
- Parses and structures the order data
- Filters results deterministically
- Returns clean JSON with `orderId`, `buyer`, `state`, and `total`

The project supports both a CLI mode and a demo UI mode.

## Files to know

- `main.py`: the core agent pipeline and Flask API
- `raftinterview/dummy_customer_api.py`: the fake order API
- `raftinterview/README.md`: project README with setup and architecture
- `INTERVIEW_PREP.md`: this notes file

## What I built

- A robust fetch step that reads the customer API and finds any order-like text in JSON
- A parsing step that uses OpenRouter model calls when available
- A deterministic fallback parser using regex in case the model cannot be used
- A request parser that turns natural language into exact filter rules
- A filter step that applies the rules locally and returns stable JSON
- A runtime audit and evidence layer to track source coverage and hallucination checks

## Architecture overview

1. `fetch_orders()`
   - Calls the customer API
   - Extracts all string values recursively
   - Keeps only strings containing the word `order`
   - Splits them into chunks for safe model input

2. `parse_orders()`
   - If `OPENROUTER_API_KEY` is set, calls `parse_chunk_with_openrouter()`
   - The model receives a strict JSON extraction prompt
   - Extracted JSON is validated and verified against the original source text
   - If verification fails, a deterministic regex parse is used as fallback

3. `parse_request()`
   - Extracts state, city, buyer, order id, total, and item filters from user text
   - Uses fuzzy matching, aliases, and natural language patterns
   - Infers ranking requests like "highest" or "lowest"

4. `filter_orders()`
   - Applies filters deterministically in code
   - Uses exact state matching, fuzzy buyer/city matching, and total comparisons
   - Returns structured JSON sorted by order ID

5. `finalize()`
   - Adds runtime diagnostics, model provider info, metrics, audit records, and anomalies

## Why this design

- **Handles edge cases**: The agent guards against context window overflow by chunking raw text.
- **Prevents hallucination**: It verifies every returned field against the source string before including it.
- **Avoids strict schema assumptions**: It searches the API response recursively rather than depending on a fixed field name.
- **Keeps output deterministic**: Model temperature is `0`, and filtering/sorting happen in local code.
- **Works without external dependencies**: LangGraph is optional and there is a sequential fallback path.

## How to run it

### Run full demo

From `raftinterview/`:

```bash
npm start
```

Then open `http://localhost:3000`.

### Run CLI only

From the repo root:

```bash
python3 main.py "Show me all orders where the buyer was located in Ohio and total value was over 500."
```

### Set up environment

Create a `.env` file in the repo root with:

```bash
OPENROUTER_API_KEY=your_openrouter_key
```

If you do not have an API key, the agent still runs with deterministic fallback logic.

## What to say in the interview

### If they ask what problem you solved

"I built an AI agent that fetches messy customer order text, structures the data, applies natural language filters, and returns deterministic JSON. The focus was on robustness, preventing hallucination, and handling schema drift."

### If they ask how you handled unpredictable API data

"I recursively scan the response JSON for any strings containing the word `order`, so the code does not depend on a fixed field like `raw_orders`. That makes the agent resilient to schema changes."

### If they ask how you prevented hallucinations

"Every field returned by the model is checked against the raw source text. If the model output cannot be verified, the system falls back to deterministic parsing. The final response is generated by local code, not directly from the model."

### If they ask why you still included a fallback parser

"Because external model calls can fail or be unavailable. The fallback parser guarantees the system still works with the provided dummy API and keeps the app runnable without an API key."

### If they ask about determinism

"Model calls use `temperature=0`, and the final filtering, sorting, and JSON formatting are done in local code. That means the same query will produce the same structured response consistently."

### If they ask what extra features you added

- Audit records proving that returned fields were supported by source text
- Metrics such as coverage, average order value, and state breakdown
- Anomaly detection for unusually large or small orders
- A React UI demo built into the repo

### If they ask how this runs with one command

`npm start` runs a Node script that launches the Flask API and the React app together. For CLI usage, `python3 main.py ...` runs the same agent pipeline directly.

## Quick points to mention

- The agent is built around a single pipeline in `main.py`
- It includes both a model-based path and a regex fallback path
- It extracts filters from natural language using fuzzy matching and regex
- It includes runtime audit and evidence for model source verification
- It is designed to be stable and deterministic

## Useful implementation details

- `parse_orders()` calls the model with a strict JSON extraction prompt
- `verify_or_fallback()` validates the model output against the raw order source
- `ORDER_RE` is the deterministic regex used to parse messy text
- `parse_request()` converts user text into filter metadata for `filter_orders()`
- The final JSON only includes `orderId`, `buyer`, `state`, and `total`

## Notes on deployment

- This repo is designed to run locally and does not require cloud deployment
- If the environment has `OPENROUTER_API_KEY`, the model path is used; otherwise the fallback is used
- The front-end is a demo, not required for the core agent functionality
